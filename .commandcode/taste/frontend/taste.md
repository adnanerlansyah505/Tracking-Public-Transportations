# Frontend

- Expects pages/components to be wired to real API data rather than dummy/mock datasets. Confidence: 0.7
- Wants empty states handled explicitly wherever a list/section can have no data (a friendly "nothing here yet" message/panel instead of blank or broken UI). Confidence: 0.7
- Cares about mobile responsiveness: expects the mobile layout to be handled deliberately (e.g. stacking/reordering columns, responsive heights, truncation), not just the desktop view. Confidence: 0.7
- Prefers building UI with Nuxt UI components rather than hand-rolled markup. Confidence: 0.7
- Cares about avoiding UI flashes/stale states: expects a loading or boot indicator (global progress bar, spinner overlay) so the wrong screen — e.g. the login page before auth resolves — is never shown briefly. Confidence: 0.6
- Expects authorization to be enforced comprehensively, not just one-way: already-signed-in users should be kept off login/register pages, and pages should be restricted per role (admin/driver/passenger). Confidence: 0.55
- Likes self-serve in-app guidance — tutorial/instruction modals that explain how to complete a task (e.g. how to obtain lat/long for stops), placed on the page where that user actually performs the action. Confidence: 0.5
- Wants a dedicated in-app help/support page that documents general, role-specific information (separate guidance for passenger/driver/admin, plus getting-started and FAQ) rather than leaving users without written help. Confidence: 0.5
- Prefers soft, non-blocking prompts when required setup is missing (e.g. a "vehicle information required" banner) over hard redirects that block navigation until a form is completed. Confidence: 0.5
- Wants the interface light-themed only: surfaces like modals should render white, not flip dark with the OS theme. Confidence: 0.6
- Expects the app not to fire auth requests that are guaranteed to fail: an anonymous/not-yet-authenticated visitor should trigger zero calls to `/auth/me` or `/auth/refresh`, with session restoration gated on there actually being a session (access token or a non-secret hint). Confidence: 0.6
- Prefers WhatsApp (wa.me deep links, with a prefilled message) as the contact channel for admins to reach users from the review UI. Confidence: 0.5
- Expects data to stay current live: wants real-time, server-pushed updates (e.g. notifications over a socket) instead of polling or manual refresh, and is comfortable adding real-time dependencies (chose Socket.IO over a dependency-free SSE approach) to get a genuine two-way channel. Confidence: 0.55
- Expects shared pages to be role-aware: a page a user lands on after login (public landing / dashboard) should surface the features relevant to the signed-in role — a driver sees a "find passengers" flow, a passenger sees the "find nearest angkot" flow — rather than showing every role the same passenger-oriented controls. Confidence: 0.5
- Wants the interface to adapt automatically to the user's context/location rather than requiring manual selection: the map should detect the user's city and load that city's network on its own, switching when the user moves, instead of making the user pick a city. Confidence: 0.5
- Expects role-specific features to reach parity and be surfaced everywhere relevant: when a feature already exists for one role (e.g. a driver's route display), asks for the same capability for other roles that need it ("just like the one for the driver") and wants it added to every pertinent page (both the passenger dashboard and the landing page) rather than only where it was first built. Confidence: 0.5
- Wants sensitive capabilities to be explicitly opt-in rather than automatic — drivers get a confirmation prompt on login to enable location sharing (off by default, revocable, and gated on explicit user action), and a passenger's location is only shared/broadcast when the passenger explicitly triggers a search, reflecting a privacy-conscious stance. Confidence: 0.6
